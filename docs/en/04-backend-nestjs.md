## Part A: the concepts

### NestJS

NestJS is a framework for building servers on Node.js. Its structure deliberately resembles Angular: classes with **decorators** and **dependency injection**. If you have read chapter 3, much of it will look familiar.

| Concept | What it is | Angular equivalent |
|---|---|---|
| **Module** (`@Module`) | Groups related controllers and services into one feature, and declares what it shares with other modules. | `NgModule` in older Angular |
| **Controller** (`@Controller`) | Receives HTTP requests. Each method handles one URL and HTTP verb. | A page component, but for HTTP instead of screens |
| **Service / provider** (`@Injectable`) | Holds the logic. Controllers stay thin and call services. | Service |
| **Dependency injection** | Services are requested through the constructor, and Nest supplies them. | `inject(...)` |
| **Pipe** | Validates or transforms incoming data before it reaches the controller. | (different from Angular pipes) |
| **DTO** | *Data Transfer Object*: a class describing the expected request body, with validation rules. | none |

A request travels through the layers like this:

```
HTTP request
   │
ValidationPipe          rejects malformed bodies (via the DTO's rules)
   │
Controller method       @Post() create(@Body() dto)  → reads the request
   │
Service                 business logic, database, queue
   │
JSON response
```

A controller method in full:

```ts
@Controller('api/analyses')              // every route below starts with /api/analyses
export class AnalysesController {
  constructor(private readonly analyses: AnalysesService) {}   // injected by Nest

  @Post()                                // POST /api/analyses
  create(@Body() dto: CreateAnalysisDto) {   // @Body() = the parsed JSON body
    return this.analyses.create(dto.repoUrl);
  }

  @Get(':id')                            // GET /api/analyses/123
  getById(@Param('id') id: string) {     // @Param('id') = "123"
    return this.analyses.getById(id);
  }
}
```

Whatever the method returns (or resolves to, for a Promise) is sent back as JSON. Throwing `BadRequestException` produces a 400, `NotFoundException` a 404, and so on.

### Prisma: the database layer

Prisma is an **ORM**: it lets the code use the database through typed TypeScript objects instead of SQL strings.

1. **`prisma/schema.prisma`** describes the tables (Prisma calls them *models*) and their columns.
2. **`prisma migrate dev`** compares the schema with the database and writes a **migration**: a SQL file that brings the database up to date. Migrations are kept in `prisma/migrations/`, in date order, and committed to git, so every developer's database ends up identical.
3. **`prisma generate`** produces a typed client from the schema. After that, code like this is fully type-checked:

   ```ts
   const run = await this.prisma.analysisRun.findUnique({ where: { id } });
   //    ^ the type of `run` is derived from the AnalysisRun model
   ```

**After every change to `schema.prisma`, run `npm run prisma:migrate`.** It creates the migration, applies it, and regenerates the client.

### BullMQ and Redis: the job queue

An analysis can take minutes, far longer than an HTTP request should stay open. The work is therefore split in two:

- The **controller** writes a job to a queue stored in Redis and replies immediately.
- A **worker** (`AnalysisProcessor`) takes jobs from the queue one at a time and runs them.

BullMQ is the queue library, and `@nestjs/bullmq` connects it to Nest. In DebtMap the worker runs **inside the same process** as the HTTP server: there is one process to start, not two. Concurrency is fixed at 1, because one analysis (a clone of up to 1 GB plus the scanners) already uses the whole resource budget of a small server.

## Part B: `apps/api` file by file

### What the tools generated, and what is ours

The Nest CLI (`nest new`) normally creates `main.ts`, `app.module.ts`, an example `app.controller.ts` and `app.service.ts`, a `test/` folder, and `nest-cli.json`. In this project the example controller, service, and `test/` folder were removed. Tests are written with Vitest and sit next to the code they test, as `*.spec.ts` files.

`prisma init` creates `prisma/schema.prisma` and, in Prisma 7, `prisma.config.ts`. The migration folders are generated by `prisma migrate dev` from our schema.

```
apps/api/
├── package.json            generated, edited  Dependencies and scripts
├── nest-cli.json           generated          Tells the Nest CLI where the source lives
├── tsconfig.json           ours               Extends tsconfig.base.json; adds decorator settings
├── prisma.config.ts        generated, edited  Loads the root .env so the Prisma CLI finds DATABASE_URL
├── prisma/
│   ├── schema.prisma       generated, edited  The database tables (all of the content is ours)
│   └── migrations/         generated          SQL produced from the schema. Never edit by hand.
│       ├── 20260826071525_init/
│       ├── 20260827090000_security_findings/
│       └── migration_lock.toml
└── src/
    ├── main.ts             generated, edited  Starts the server: validation, CORS, port
    ├── app.module.ts       generated, edited  Root module: config, queue, and all feature modules
    ├── config/             ours               Environment variable validation
    ├── analyses/           ours               The main feature: endpoints, logic, worker
    ├── github/             ours               Checks repositories against the GitHub API
    ├── health/             ours               Health-check endpoint
    ├── prisma/             ours               Database connection as an injectable service
    ├── quota/              ours               Daily usage limits, stored in Redis
    └── security/           ours               Cache of vulnerability advisories
```

### Folder-per-feature

Every folder under `src/` is one **feature**, usually laid out like this:

```
analyses/
├── analyses.module.ts      wires the feature together
├── analyses.controller.ts  HTTP endpoints
├── analyses.service.ts     logic
├── analysis.processor.ts   queue worker
├── analysis.queue.ts       queue name, job shape, concurrency
└── dto/
    └── create-analysis.dto.ts   request body validation
```

The file-name suffix tells you what a file is: `.module`, `.controller`, `.service`, `.processor`, `.dto`, `.spec` (test).

### `main.ts`: startup

1. Creates the Nest application from `AppModule`.
2. Installs a global `ValidationPipe`. Unknown fields in a request body are **rejected**, not silently dropped, so a client sending the wrong shape finds out immediately.
3. Enables CORS for the origins in `CORS_ORIGINS`, for GET and POST only.
4. Listens on `PORT` (3100 in `.env`).

### `app.module.ts`: the root module

| Import | Purpose |
|---|---|
| `ConfigModule.forRoot({ validate })` | Loads `.env` (from `apps/api` or the repository root) and validates it at startup. A missing `DATABASE_URL` stops the server with a clear message instead of failing on the first request. |
| `BullModule.forRootAsync` | Connects BullMQ to Redis using `REDIS_URL`. Keeps the last 50 completed and 100 failed jobs. |
| `PrismaModule`, `QuotaModule` | Marked `@Global()`, so every other module can inject their services without importing them. |
| `GitHubModule`, `AnalysesModule` | Features |
| `HealthController` | Registered directly, since it has no module of its own |

### `config/configuration.ts`

Declares every environment variable as a class property with validation decorators (`@IsInt()`, `@Min(1)`, …) and a default value. To add a setting: add a property here, add it to `.env.example`, and read it with `config.get('NAME')`. The full list is in [chapter 6](06-running-locally.md#environment-variables).

### `analyses/`: the core feature

**The endpoints** (`analyses.controller.ts`):

| Method and path | Returns | Used by |
|---|---|---|
| `POST /api/analyses` with body `{ "repoUrl": "…" }` | The new run's id and status | Home page |
| `GET /api/analyses/:id/status` | Status, stage, and progress only (small) | Results page, every 2 seconds while running |
| `GET /api/analyses/:id` | The full result, with every file | Results page, once finished |
| `GET /api/analyses/shared/:slug` | The same, looked up by share slug | Share links |
| `GET /api/analyses/:id/files/:fileId` | One file's details | File page |
| `GET /api/analyses/history?repoUrl=…` | Scores of past runs of a repository | Reserved for the trend view (M4) |

**What happens on `POST`** (`analyses.service.ts`, method `create`):

1. Parse the URL with `parseRepoUrl` from `@debtmap/shared`.
2. If this repository already has a run in progress, **return that run** instead of starting a second one.
3. Ask GitHub whether the repository exists, is public, and is within `MAX_REPO_SIZE_MB` (`GitHubService`).
4. Spend one unit of the daily repository budget (`QuotaService`). If the budget is exhausted, reply 503.
5. Create or update the `Repository` row, and create an `AnalysisRun` row with status `QUEUED` and a random share slug.
6. Add a job to the queue. The job id is the run id. A failed job is **not retried**, because analysis failures are almost always deterministic.
7. Reply with the run's status.

**The worker** (`analysis.processor.ts`):

- On startup it deletes clone folders left behind by a previous process.
- For each job it calls `analyzeRepository(...)` from `@debtmap/analyzer` with settings taken from the environment.
- The analyzer reports progress through a callback. The processor writes each stage to the run row, translating fine-grained analyzer stages into the coarser `RunStatus` shown in the UI:

  | Analyzer stage | `RunStatus` |
  |---|---|
  | `cloning` | `CLONING` |
  | `discovering`, `git-metrics`, `ast-metrics`, `scoring` | `ANALYZING` |
  | `security` | `SCANNING` |

- On success it saves all file metrics in one transaction and sets `COMPLETED`. On failure it sets `FAILED` with the error message.

### `github/github.service.ts`

Calls `GET https://api.github.com/repos/:owner/:name` **before** cloning. It reads the default branch, size, and visibility. It throws a specific error for "not found / private", "too large", and "rate limited", and each becomes a clear HTTP error for the user. It sends `GITHUB_TOKEN` when one is set; without it GitHub allows only 60 requests per hour.

### `quota/`

`QuotaService` keeps daily counters in Redis (`repos`, `gemini`) that reset every day. They keep usage within free-tier limits (`DAILY_REPO_BUDGET`, `AI_DAILY_REQUEST_BUDGET`). `redis.provider.ts` creates the shared Redis connection.

### `security/advisory-cache.service.ts`

OSV.dev returns only vulnerability ids in its batch response, so each vulnerability needs a second request for its details. Advisories are the same for every repository that uses the same package, so they are cached in the `vulnerability_cache` table for 7 days. The analyzer defines the cache interface (`AdvisoryCache`), and this service implements it on top of Postgres. That way the analyzer itself never depends on a database.

### `health/health.controller.ts`

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Returns `ok`, uptime, and how much of today's quotas is left |
| `POST /api/health/warmup` | Opens the database connection ahead of time. Hosted Postgres (Neon) sleeps when idle; calling this before a demo avoids a slow first request. |

### `prisma/prisma.service.ts`

Extends `PrismaClient` so that the database client can be injected like any other service. It connects through the `pg` driver adapter (required by Prisma 7), with a small connection pool.

### The database: `schema.prisma`

```
Repository 1 ──── * AnalysisRun 1 ──── * FileMetric 1 ──── 0..1 AiExplanation

VulnerabilityCache   (standalone; shared by all runs)
```

| Table | One row per | Key columns |
|---|---|---|
| `repositories` | GitHub repository | `url` (unique, e.g. `github.com/owner/name`), `owner`, `name`, `defaultBranch` |
| `analysis_runs` | Analysis | `status`, `stage`, `progress`, `error`, `commitSha`, `securityScore`, `bugPronenessScore`, `scanOutcomes` (JSON), `repositoryFindings` (JSON), `shareSlug` |
| `file_metrics` | File in a run | Raw: `churnCommits`, `churnLinesChanged`, `bugCommits`, `cyclomaticComplexity`, `maxNestingDepth`, `loc`. Scores: `churnScore`, `bugScore`, `complexityScore`, `bugPronenessScore`, `securityScore`. `securityFindings` (JSON). |
| `ai_explanations` | Explained file (M3) | Summary and recommendation in English and Hebrew, `cacheKey` |
| `vulnerability_cache` | OSV advisory | `osvId`, `severity`, `cvss`, `fixedVersions` (JSON), `fetchedAt` |

Deleting a repository deletes its runs, and deleting a run deletes its file metrics (`onDelete: Cascade`).

To look at the data in a browser: `npm run prisma:studio`.

### Common tasks

| Task | How |
|---|---|
| Start the API | `npm run dev:api` from the root. It restarts automatically when you save a file under `apps/api/src`. |
| Add an endpoint | Add a method to a controller, with the logic in the matching service. Put the response type in `packages/shared/src/dto.ts` so the frontend can use it too. |
| Add a feature area | Create `src/<feature>/` with a `.module.ts`, `.controller.ts`, and `.service.ts`, then add the module to `imports` in `app.module.ts`. |
| Change the database | Edit `prisma/schema.prisma`, then `npm run prisma:migrate`. Commit the new migration folder. |
| Changed code in `packages/analyzer` or `shared` | Rebuild it (`npm run build -w @debtmap/analyzer`) and restart the API. The API's watch mode only watches its own folder. |
| Run tests | `npm test -w @debtmap/api` |
