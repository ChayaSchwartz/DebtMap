# 5. The analyzer and shared packages

[Docs index](../README.md) · Previous: [Backend (NestJS)](04-backend-nestjs.md) · Next: [Running locally](06-running-locally.md)

Both packages are plain TypeScript, with no Angular or NestJS. Nothing in them was generated by a tool: **everything here is `ours`**, apart from the compiled `dist/` folders.

---

## `packages/shared`: one source of truth

```
packages/shared/
├── package.json        "main": "./dist/index.js": importers get the compiled output
├── tsconfig.json       Compiles to CommonJS, which both Nest and Angular can consume
└── src/
    ├── index.ts        Re-exports everything below
    ├── dto.ts          The shapes of every API request and response
    ├── risk.ts         Severities, security sources, the SecurityFinding shape
    ├── scoring.ts      Scoring formulas, thresholds, colour bands
    ├── repo-url.ts     The GitHub URL parser
    └── *.test.ts       Tests
```

### Why a shared package exists

The browser, the server, and the engine all need to agree on the same facts: what a valid repository URL is, what a response looks like, and what score counts as "high". If each had its own copy, the copies would drift apart. Here there is exactly one copy, and the TypeScript compiler fails the build of any project that uses it wrongly.

| File | Used by web | Used by api | Used by analyzer |
|---|---|---|---|
| `repo-url.ts` (`parseRepoUrl`) | Home page, before submitting | DTO validation | Clone URL |
| `dto.ts` | Response types in `AnalysisService` | Building responses | none |
| `scoring.ts` | `toRiskBand` for colours | none | All score calculations |
| `risk.ts` | Showing findings | Storing findings | Producing findings |

### `repo-url.ts`

`parseRepoUrl(input)` accepts what people actually paste (`github.com/a/b`, `https://github.com/a/b/tree/main/src`, `git@github.com:a/b.git`, …) and returns `{ owner, name, canonical, cloneUrl }`, or `null` if the input is not a GitHub repository URL. Only github.com is accepted.

### `scoring.ts`: how scores are calculated

**Bug-proneness of a file** (0–100):

```
bugProneness = 0.3 × churnScore + 0.4 × bugScore + 0.3 × complexityScore
```

Each input is a **percentile rank within the repository**. A `complexityScore` of 80 means the file is more complex than 80% of the files in that repository. Bug-fix history carries the most weight because it is direct evidence: the file has already broken before.

**Security of a file** (0–100) depends on its **worst** finding, not on how many it has:

| Worst severity | Base score |
|---|---|
| critical | 90 |
| high | 72 |
| medium | 45 |
| low | 20 |
| info | 5 |

Each extra finding of that same severity adds 2 points, up to +10 in total.

**Repository scores** use an **absolute** scale instead of ranks. Percentile ranks always average to roughly the same value, so a repository-level number built from them would never move between runs. The absolute scale uses a curve that reaches 50 at a reference point (complexity 40, 12 commits, 5 bug-fix commits) and approaches 100 without ever clipping.

**Colour bands** (`toRiskBand`): 85 and above is `critical`, 70+ is `high`, 40+ is `moderate`, and below 40 is `low`. 70 is also `HIGH_RISK_THRESHOLD`, the cut-off for AI explanations.

## `packages/analyzer`: the engine

```
packages/analyzer/
├── package.json        Dependencies: simple-git, ts-morph, tinyglobby
├── tsconfig.json
└── src/
    ├── index.ts        Public API: what the backend may import
    ├── cli.ts          Command-line entry: npm run analyze -- <url>
    ├── analyze.ts      The pipeline: calls every stage in order
    ├── types.ts        Options, defaults, result shapes, progress events
    ├── clone.ts        git clone, cleanup, workspace sweeping
    ├── discover.ts     Which files to analyse
    ├── git-metrics.ts  Churn and bug-fix commits from git log
    ├── complexity.ts   Cyclomatic complexity and nesting via ts-morph
    ├── normalize.ts    Percentile ranks and repository aggregates
    ├── security/
    │   ├── index.ts    Runs the three scanners in sequence; maps findings to files
    │   ├── process.ts  Safe process spawning: no shell, timeout, output cap
    │   ├── semgrep.ts  Code-pattern scanner
    │   ├── gitleaks.ts Secret scanner, over the full git history
    │   ├── lockfile.ts Reads package-lock.json as text
    │   ├── osv.ts      Queries OSV.dev for vulnerable dependency versions
    │   ├── cvss.ts     Turns CVSS vectors into severities
    │   └── types.ts
    └── *.test.ts       Tests, next to the file they test
```

### Why it has no framework

The engine is the riskiest part of the product: it is where the numbers come from. Keeping it free of NestJS means it can be run and tuned on real repositories from the command line, without a database, a queue, or a server:

```bash
npm run analyze -- https://github.com/sindresorhus/got --top 15
npm run analyze -- <url> --no-security        # skip the scanners (much faster)
npm run analyze -- <url> --churn-months 12    # shorter history window
```

The backend uses the same code through `analyzeRepository(...)`.

### The pipeline (`analyze.ts`)

| # | Stage | File | What it does |
|---|---|---|---|
| 1 | `cloning` | `clone.ts` | `git clone` with full history (needed by Gitleaks) into `WORKSPACE_DIR/<random-id>`. Hardened: symlinks disabled, `ext::` transport blocked, no interactive prompts. |
| 2 | `discovering` | `discover.ts` | Collects `.ts .js .mjs .cjs .mts .cts`, excluding `node_modules`, `dist`, `build`, `vendor`, `*.min.js`, `*.d.ts`, and similar. Tests are **included** on purpose. Files over 1 MB are skipped as generated bundles (`MAX_SOURCE_FILE_BYTES`, the same limit Semgrep uses). If there are more than `MAX_FILES`, only the largest are kept and the run is marked *truncated*. |
| 3 | `git-metrics` | `git-metrics.ts` | One `git log --numstat` over the last 24 months. Per file: number of commits, lines changed, and commits whose message looks like a bug fix (`fix`, `bug`, `hotfix`, `regression`, `crash`, `broken`, …). |
| 4 | `ast-metrics` | `complexity.ts` | Parses every file with `ts-morph` and counts cyclomatic complexity, maximum nesting depth, and lines of code. Only parsing happens: no type checking, no `npm install`, nothing executed. |
| 5 | `security` | `security/` | Semgrep, then Gitleaks, then OSV. Each one can be `ok`, `skipped`, or `failed` without stopping the others. |
| 6 | `scoring` | `normalize.ts` + `shared/scoring.ts` | Percentile ranks, per-file scores, repository scores. |

The clone is deleted at the end, including when a stage fails.

### The security scanners

| Scanner | Looks at | Finds | Needs |
|---|---|---|---|
| **Semgrep** | Current files | Dangerous patterns such as `eval`, SQL built from strings, weak crypto | The `semgrep` program, plus its rule files |
| **Gitleaks** | All of git history | Committed passwords, API keys, and tokens, including ones that were deleted later | The `gitleaks` program |
| **OSV** | `package-lock.json` | Dependencies with known vulnerabilities | Network access to `api.osv.dev` |

Rules the security code always follows, because every analysed repository is untrusted:

- **The repository's code is never run.** No `npm install` (that would run a stranger's `postinstall` scripts), no build, no tests.
- **Scanners are started without a shell** (`process.ts`), so a malicious file name cannot become a command.
- **Every scanner has a timeout and an output cap.** One that floods its output is killed.
- **Gitleaks runs with `--redact`**, so a real secret is never stored in the database or shown in the UI.

Findings for paths that are not among the analysed files (a lockfile, or a file deleted from history) become **repository-level findings**.

### Ports: how the engine avoids depending on the database

The OSV integration needs a cache, but the engine must not know about Postgres. It therefore declares an interface, `AdvisoryCache`, and accepts any implementation of it:

- The backend passes `AdvisoryCacheService` (Postgres, see chapter 4).
- The CLI and the tests pass `createMemoryAdvisoryCache()` (in memory).

Progress reporting (`onProgress`) and logging (`logger`) work the same way: the caller decides where they go.

### Tests

```bash
npm test -w @debtmap/analyzer
npm test -w @debtmap/shared
```

Tests use Vitest and sit next to the code they test (`complexity.ts` ↔ `complexity.test.ts`). Some create small real git repositories in a temporary folder, so `git` must be installed.

### After changing code here

The apps import the compiled `dist/` output, not the source. After a change:

```bash
npm run build -w @debtmap/shared      # if you changed shared
npm run build -w @debtmap/analyzer    # if you changed the analyzer (or shared)
```

Then restart the API. The CLI (`npm run analyze`) runs the TypeScript source directly through `tsx`, so it needs no build.
