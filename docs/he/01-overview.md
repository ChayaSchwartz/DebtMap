# 1. סקירה כללית

[תוכן העניינים](../README.md) · הבא: [מבנה הריפו](02-repository-structure.md)

## מה DebtMap עושה

המשתמש מדביק כתובת של ריפו ציבורי ב-GitHub. DebtMap מוריד אותו, מודד כל קובץ TypeScript ו-JavaScript, ומציג טבלה מדורגת עם שני ציונים נפרדים לכל קובץ:

- **אבטחה (Security)**: כמה הקובץ חשוף. הציון מגיע משלושה סורקים: Semgrep (דפוסי קוד מסוכנים), Gitleaks (סיסמאות ומפתחות שנכנסו להיסטוריית git) ו-OSV.dev (פרצות ידועות בתלויות).
- **נטייה לבאגים (Bug-proneness)**: כמה סביר שהקובץ יישבר. הציון בנוי משלושה גורמים: כמה הקובץ משתנה (*churn*), כמה קומיטים של תיקון באג נגעו בו, וכמה הקוד שלו מורכב.

שני הציונים לעולם לא מתאחדים למספר אחד. סיסמה שדלפה וקובץ שפשוט קשה לשנות הם בעיות שונות, עם בעלים שונים ופתרונות שונים.

## ניתוח אחד, מתחילתו ועד סופו

1. **המשתמש שולח כתובת.** דף הבית בודק את הכתובת מקומית עם `parseRepoUrl` מתוך `packages/shared`, ואז שולח `POST /api/analyses`.
2. **ה-API בודק את הריפו לפני שהוא מוריד אותו.** `GitHubService` שואל את ה-API של GitHub אם הריפו קיים, אם הוא ציבורי ואם הוא בגבולות הגודל. ה-API יוצר שורת `AnalysisRun` בסטטוס `QUEUED`, מכניס עבודה לתור ב-Redis, ומחזיר מיד את מזהה ההרצה.
3. **הדפדפן שואל שוב ושוב (polling).** דף התוצאות קורא ל-`GET /api/analyses/:id/status` כל שתי שניות ומציג את השלב הנוכחי.
4. **ה-worker לוקח את העבודה.** `AnalysisProcessor`, שרץ בתוך תהליך ה-API, קורא ל-`analyzeRepository` מתוך `packages/analyzer`, וזה עובר בשלבים הבאים:

   | שלב | מה קורה |
   |---|---|
   | `cloning` | `git clone` עם כל ההיסטוריה לתיקייה זמנית |
   | `discovering` | איתור קבצי `.ts`/`.js`, בלי `node_modules`, `dist`, קבצים מכווצים וכדומה |
   | `git-metrics` | מעבר אחד על `git log`: קומיטים לכל קובץ, שורות שהשתנו, קומיטים של תיקון באג |
   | `ast-metrics` | פענוח כל קובץ עם `ts-morph` ומדידת מורכבות וקינון. שום דבר לא מורץ. |
   | `security` | Semgrep, אחריו Gitleaks, אחריו OSV, אחד אחרי השני |
   | `scoring` | הפיכת המספרים הגולמיים לציונים בין 0 ל-100 |

   אחרי כל שלב ה-worker מעדכן את `status`, `stage` ו-`progress` של ההרצה במסד הנתונים. את הערכים האלה קורא ה-polling משלב 3.
5. **התוצאות נשמרות.** שורת `FileMetric` אחת לכל קובץ, וגם ציונים ברמת ההרצה ותוצאות הסורקים. השכפול הזמני נמחק.
6. **הדף מציג את התוצאות.** כשהסטטוס מגיע ל-`COMPLETED`, הדף מביא את `GET /api/analyses/:id` ומציג את הטבלה. לכל הרצה יש גם קישור שיתוף שאי אפשר לנחש: `/shared/:slug`.

## מונחים שיופיעו בקוד

| מונח | משמעות |
|---|---|
| **Run** (`AnalysisRun`) | ניתוח אחד של ריפו אחד בקומיט אחד. לריפו יכולות להיות הרבה הרצות. |
| **Churn** | כמה קובץ משתנה: מספר הקומיטים והשורות שהשתנו. כברירת מחדל נספרים 24 החודשים האחרונים. |
| **Bug commit** | קומיט שההודעה שלו נראית כמו תיקון (`fix`, `bug`, `hotfix` וכו'). |
| **Cyclomatic complexity** | מספר המסלולים הבלתי תלויים בקוד. כל `if`, לולאה, `case`, `&&`, `catch` וכו' מוסיף אחד. |
| **Percentile rank** | הציונים של קבצים הם יחסיים: 90 פירושו "גרוע מ-90% מהקבצים בריפו הזה", ולא ציון מוחלט. |
| **Finding** | ממצא אחד שסורק דיווח עליו. |
| **Repository-level finding** | ממצא שלא שייך לאף קובץ שנותח. למשל תלות פגיעה, או סוד בקובץ שנמחק מאז. |
| **Scan outcome** | האם כל סורק רץ (`ok`), לא היה זמין (`skipped`) או קרס (`failed`). הממשק מציג את זה כדי שלא יתבלבלו בין "לא נמצא כלום" לבין "בכלל לא רץ". |
| **Slug** | המזהה האקראי בקישור השיתוף. |
